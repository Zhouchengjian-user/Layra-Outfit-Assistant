# Layra 穿搭助手 · 火山引擎迁移方案

> 状态：方案已对齐，待确认后实施。本文件是迁移的唯一事实来源，实施时按阶段推进。

## 1. 背景与目标

将「Layra 穿搭助手」从 Cloudflare 生态**彻底迁移到火山引擎（国内云）**，用火山引擎「函数服务 veFaaS」承载。

**已对齐的决策记录（2026-08）：**

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 迁移动机 | 彻底换成国内云，放弃 Cloudflare |
| 2 | 载体 | veFaaS「Web 应用函数」+ 容器镜像（Native 运行时，不限语言） |
| 3 | 框架 | vinext → 标准 Next.js（Node 服务） |
| 4 | 数据库 | D1(SQLite) → 火山引擎云数据库 MySQL |
| 5 | 图片存储 | R2 → TOS 对象存储（S3 兼容） |
| 6 | 域名 | 暂无自有域名，先用 veFaaS 默认公网域名，后续备案再绑自定义域名 |
| 7 | AI 能力 | 阿里云百炼（Qwen）不变 |

## 4. 分阶段实施步骤

### 阶段 0：账号与服务准备（无代码）
1. 火山引擎账号实名认证；开通 veFaaS 函数服务 + 跨服务授权（子账号需 `veFaaSFullAccess`）。
2. 开通 **TOS 对象存储**，创建 Bucket（如 `yida-wardrobe`），记录 Endpoint / Region。
3. 开通 **云数据库 MySQL**（RDS MySQL 或 veDB MySQL），创建实例 + 数据库 `yida` + 账号，**与 veFaaS 函数同地域、同 VPC**。
4. 开通 **镜像仓库 CR**（容器镜像服务），记录命名空间与仓库地址。
5. 准备火山引擎 AccessKey（AK/SK）用于 CLI/镜像推送。

### 阶段 1：框架迁移 vinext → Next.js（工作量最大）
- 移除 `vinext`、`@cloudflare/vite-plugin`、`wrangler`、`build/`、`.wrangler/`、`worker/`、`.openai/`、`cloudflare-env.d.ts`。
- 引入 Next.js（当前 `package.json` 已有 `@next/eslint-plugin-next`，需补 `next`、`@next/...`）。
- `package.json` scripts 改为 `next dev / build / start`。
- 恢复/新建 `next.config.ts`（配置 standalone 输出、图片域等）。
- `app/` 目录为 Next.js App Router 结构，基本可保留；`app/layout.tsx`、`app/page.tsx` 需按 Next.js 标准补齐 metadata 等。
- `app/lib/server-env.ts`：去掉 `cloudflare:workers`，直接读 `process.env`。
- `app/lib/api-client.ts`（浏览器端）基本不变。

### 阶段 2：数据层 D1/SQLite → MySQL
- 新增 `app/lib/db.ts`：基于 `mysql2/promise` 的连接池封装（读 `process.env` 的 MySQL 连接串），提供 `query/execute` 及少量 helper。
- 建表逻辑从「运行时自动建表」改为「部署时执行迁移脚本」：
  - 新增 `db/mysql/0000_init.sql`（3 张表的 MySQL DDL，见 §5 映射）。
  - 移除各 route 里的 `ensureSchema` / `ensureAiTaskSchema` / `prepareSchema` 自动建表。
- 改写 5 个 route + `app/lib/ai-tasks.ts` 的 D1 调用为 mysql2（SQL 方言转换，见 §5）。
- 清理 drizzle（`db/index.ts`、`db/schema.ts`、`drizzle.config.ts`、`drizzle/`）：可删，或改为 mysql dialect 作为迁移工具（二选一，见待确认 §9-1）。

### 阶段 3：存储层 R2 → TOS
- 新增 `app/lib/storage.ts`：封装 TOS 的 `put / get / delete / head`，保持现有 key 结构不变。
  - 客户端选型：`@aws-sdk/client-s3`（S3 兼容）或 `@volcengine/tos-sdk`，见待确认 §9-2。
- 改写 6 个 route 的 R2 调用（`put/get/delete` + `writeHttpMetadata` → storage 封装 + 手动设置 Content-Type/Cache-Control）。
- 图片流式返回：改为从 TOS 读流后透传（`GET /api/wardrobe?image=`、`/api/wardrobe/source`、`/api/model-profile?image=1` 等）。

### 阶段 4：部署层 Docker + veFaaS
- 编写 `Dockerfile`（基于 `node:22-alpine`，`next build` 产物 `standalone`，`CMD ["node","server.js"]`，监听 `0.0.0.0:8000`）。
- 编写 `.dockerignore`（排除 `.next`、`node_modules`、`.env*` 等）。
- 构建并推送镜像到火山引擎镜像仓库。
- 在 veFaaS 控制台创建「Web 应用函数」：
  - 部署方式 = 镜像，选择已推送镜像；
  - Webserver 模式 = 是，监听端口 = 8000；
  - 配置环境变量（见 §7）；
  - 绑定与 MySQL 相同的 VPC/子网/安全组；
  - 设置实例规格、实例数下限（预留实例，避免冷启动）与上限；
  - 创建 HTTP 触发器 / 域名，拿到默认公网访问地址。
- 可选：用 veFaaS CLI（`vefaas`）把部署流程脚本化，纳入 `scripts/deploy.sh`。

### 阶段 5：数据迁移（D1 → MySQL、R2 → TOS）

> **已放弃（2026-08）**：旧 Cloudflare 数据经与用户确认后决定不迁移，线上从零开始。

### 阶段 6：验证与上线
- 本地 `next dev` + 本地 MySQL/TOS 联调全流程（上传 → 识别 → 商品图 → 入柜 → 推荐 → 试穿）。
- 部署到 veFaaS 后回归：`npm run build`、`npm test`（若测试仍适用）、手工冒烟。
- 灰度/切换：确认默认域名可用后，替换旧 `*.chatgpt.site` 演示地址。

## 5. SQLite → MySQL 语法映射清单

| SQLite | MySQL |
|---|---|
| `TEXT PRIMARY KEY` | `VARCHAR(64) PRIMARY KEY`（uuid 用 `VARCHAR(36)`） |
| `text` | `TEXT` / `VARCHAR(n)` |
| `integer`（时间戳） | `BIGINT` |
| `PRAGMA table_info(t)` | `SELECT COLUMN_NAME FROM information_schema.COLUMNS WHERE TABLE_NAME='t'` |
| `INSERT OR IGNORE INTO ...` | `INSERT IGNORE INTO ...` |
| `ON CONFLICT(owner_id) DO UPDATE SET ...` | `ON DUPLICATE KEY UPDATE ...` |
| `?` 占位符 | `?` 占位符（mysql2 同样支持） |
| 运行时 `CREATE TABLE IF NOT EXISTS` | 改为部署时执行 `db/mysql/0000_init.sql` |

MySQL DDL 骨架（以 `wardrobe_items` 为例）：

```sql
CREATE TABLE wardrobe_items (
  id VARCHAR(36) PRIMARY KEY,
  owner_id VARCHAR(80) NOT NULL,
  name VARCHAR(80) NOT NULL,
  category VARCHAR(40) NOT NULL,
  color_name VARCHAR(40) NOT NULL,
  color_hex VARCHAR(12) NOT NULL,
  season VARCHAR(40) NOT NULL,
  style VARCHAR(40) NOT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'available',
  ai_tags TEXT NOT NULL,
  tag_version INT NOT NULL DEFAULT 0,
  image_key VARCHAR(255) NOT NULL,
  created_at BIGINT NOT NULL,
  INDEX idx_wardrobe_items_owner_created (owner_id, created_at)
);
```

## 6. R2 → TOS 映射

| R2 API | TOS（S3 兼容）等价 |
|---|---|
| `bucket.put(key, body, {httpMetadata:{contentType}})` | `PutObjectCommand({ Bucket, Key, Body, ContentType })` |
| `bucket.get(key)` → `object.body` | `GetObjectCommand(...)` → `Body` 流 |
| `bucket.delete(key)` | `DeleteObjectCommand(...)` |
| `object.writeHttpMetadata(headers)` | 手动设置 `Content-Type` / `Cache-Control` 响应头 |

key 结构不变，仅替换底层客户端。新增 `app/lib/storage.ts` 收敛 6 处调用。

## 8. 风险与注意事项

1. **veFaaS 超时/并发**：AI 链路最长 180s（商品图/试穿），在同步调用 15min 上限内；建议为 AI 类请求配置足够的实例数与单实例并发，预留实例降低冷启动。
2. **数据库网络**：veFaaS 函数与 MySQL 需**同 VPC 内网互通**；TOS 走公网/内网 Endpoint 均可。
3. **大图内存**：图片以流式/二进制处理，避免超大 payload；当前限制 3~12MB，MySQL 只存 key，不存图片。
4. **鉴权**：现用 `yida_owner` cookie 做匿名 owner 隔离，迁移不改变鉴权模型；上线前需确认 HTTPS（veFaaS 默认域名自带）。
5. **`Secure` cookie**：`withOwnerCookie` 里 `Secure` 标志在本地 `next dev`（HTTP）下会导致 cookie 不生效，联调时需按环境切换。
6. **数据迁移时效**：R2 对象较多时用工具批量同步；迁移窗口内可考虑只读。

## 9. 待确认 / 前置依赖

1. **Drizzle 去留**：业务当前用原生 SQL，建议**直接删除 drizzle、改用 mysql2 + SQL 迁移脚本**（更简单、少一层抽象）。是否同意？
2. **TOS 客户端**：建议用 `@aws-sdk/client-s3`（S3 兼容、生态成熟）还是火山官方 `@volcengine/tos-sdk`？默认推荐 AWS SDK v3。
3. **数据库产品**：RDS MySQL 还是 veDB MySQL？（两者均兼容，推荐 RDS MySQL，实例规格/白名单按需）。
4. **火山引擎账号/密钥**：需要你提供或开通上述服务（阶段 0），实施时需要 AK/SK 与各服务资源 ID。
